# 跨设备同步 — 改动方案

> 状态：**暂不实施**（2026-10-30 决定）。本文留作决策记录，不作为排期依据。
>
> 结论是：技术上可行（5.5 人日、零服务器），但代价不在代码，而是把产品从
> 「纯本地」挪到「默认本地、可选上云」——这个定位改动还没准备好，所以先不做。
>
> 若将来重启：仍然要从 §1 开始（先改 `SPEC.md` 的定位段），而不是从写代码开始。
> 本文与 `SPEC.md` §0「反向差异：不联网、不云同步」冲突，两者必须同步改。

---

## 0. 一句话

用 `chrome.storage.sync` 当通道，把**整团 vault 密文**（连同 password-wrapped DEK）
同步到用户自己的 Chrome 账号下。密钥不出本机，云端只有密文；零服务器、零账号体系、零成本。

---

## 1. 先决条件：改定位，不是改功能

现在 SPEC 把「不联网、不云同步」写成了**反向差异**（第 0 节）和「明确不做」（云备份）。
这个功能的性质和它正相反，所以顺序必须是：

1. 先把 SPEC §0 的反向差异从「不云同步」改成「**默认不云同步**，可选开启，云端仅存密文」
2. 同步开关**默认关闭**，且不在首屏出现任何引导——只在设置页里
3. `PRIVACY.md` 增加一节「如果你开启跨设备同步」，写清楚：数据经 Chrome Sync 存在
   Google 账号下、是密文、关闭时会从云端删除、其他设备已有的副本不会自动消失
4. 商店描述不主动宣传这个功能。它是「给需要的人的开关」，不是卖点

**如果第 1 条不接受，这个功能就别做。** 一边写「纯本地零上传」一边默默把数据放上云，
是这类产品被差评的第一原因。

---

## 2. 明确不做（防范围膨胀）

| 不做 | 原因 |
|---|---|
| 自建后端 / 账号体系 | 引入服务器成本与合规，且与「无账号」定位彻底冲突 |
| 手机端 | 浏览器扩展形态决定了做不到；要做就是另一个产品 |
| 实时同步 | 没有长连接可用，只能靠 `onChanged` 事件 + 打开时拉取 |
| 端到端加密之外的"更方便"方案 | 任何让 DEK 明文上云的简化都直接否掉 |
| 同步无密码库 | 见 §7，无密码时 DEK 是明文，绝不上云 |

---

## 3. 核心模型：一个 vault，多设备共用同一份密文

这是全篇最重要的一条，决定了后面所有设计。

现状（`crypto.ts` + `vault-service.ts`）：

- vault 整体是一团 AES-GCM 密文，AAD 为 `2fa/vault/v1`
- 这把密钥（DEK）是 **per-vault** 的，用 `dekWrap` 包起来：`password`（含 salt + iter）或 `recovery`
- 两台设备各自 `initializeVault()` 会产生**不同的 DEK**

推论：**密文层无法按账户合并**，两台设备的库在字节层面互不兼容。
所以同步的最小单位不是「账户」，是「**整个库**」，并且要有一个身份来识别「是不是同一个库」。

### 3.1 库身份

`vaultId`：16 字节随机数，base64。首次开启同步时生成，写进 `local` 的 `2fa:sync`。
它只是一个随机标识，不含任何用户信息，出现在云端明文里也无害。

### 3.2 哪些数据参与同步

| 数据 | 是否同步 | 说明 |
|---|---|---|
| `2fa:vault`（密文） | ✅ | 账户、分组、设置全在里面 |
| `2fa:dekWrap`（password 包装） | ✅ | 没有它第二台设备解不开；这是"用同一个密码打开"的前提 |
| `2fa:dekWrapRecovery` | ✅ | 换机时恢复码也要能用 |
| `2fa:meta` | ✅ | `createdAt` / `schemaVersion`，不含任何敏感信息 |
| `2fa:dek`（session 明文 DEK） | ❌ | 绝不出本机 |
| `2fa:backup:*`（每日快照） | ❌ | 每台设备各自备份，同步会撑爆 100KB |
| `2fa:ui-hint` / `2fa:sync` | ❌ | 描述的是**这台设备**的状态，跟着跑过去反而是错的 |

**关键安全点**：上云的是 `dekWrap`（被密码包住的 DEK），不是 DEK 本身。
写进 vault 的 `AAD_DEK` 保证它不能被挪去别处使用。

## 4. 云端存储结构与提交协议

### 4.1 Key 布局

```
sync:manifest          { v, vaultId, rev, epoch, chunks, bytes, schemaVersion, deviceId, updatedAt }
sync:c:{epoch}:{0..n}   每个 ≤ 6KB 的 base64 分片
```

`epoch` 是**单调递增整数**（不是时间戳），每次提交 +1。用它做代际隔离，见 4.3。

### 4.2 容量硬约束（Chrome 官方值）

| 项 | 值 | 我们的用法 |
|---|---|---|
| `QUOTA_BYTES` | 100 KB | 提交前自检，超过 90 KB 直接拒绝并解释 |
| `QUOTA_BYTES_PER_ITEM` | 8 KB | 分片切到 6 KB，留 2 KB 给 key 与 JSON 包装 |
| `MAX_ITEMS` | 512 | 单代约 15 片；靠 GC 控制在 3 代以内 |
| 写操作/小时 | 1800 | 靠 §8 的节流保证远低于此 |

容量估算：单条账户 JSON ≈ 180–220 B，加密后 base64 膨胀 ×1.37。
100 KB 实际能装约 **250–300 条**。P0 要写一个 test 用真实数据测出准确数字，
它会变成 UI 文案里的上限提示。

### 4.3 提交协议（这是整个方案的技术核心）

```
1. 生成新 epoch = old + 1
2. 先写全部分片 sync:c:{new}:{i}        ← 一次 set() 批量写
3. 最后写 manifest，rev += 1            ← 这一笔是"提交"
4. 提交成功后，删除 epoch < new-1 的所有分片（GC）
```

**为什么要 manifest 最后写**：写多片不是原子的，中途断电/崩溃会留下半套分片。
读方永远只认 manifest 指向的 epoch，所以半套数据**不可见**，不会解出半个库。

**为什么并发写不会互相污染**：两台设备同时写会分属两个 epoch，分片 key 不重叠，
最后写 manifest 的那台赢（last-write-wins）。输的那台的整代数据变成垃圾，由 GC 清掉。

**GC 的边界**：只删 `epoch < current - 1`。保留上一代是因为另一台设备可能刚写完
manifest 还没推送完，删太干净会让它在半路上失去数据。多留一代的代价约 15 个 item，
在 512 上限内完全可接受。

### 4.4 读取与校验

```
读 manifest → 若 manifest.vaultId !== local.vaultId → 外来库，走 §6 认领流程
           → 读 chunks → 拼 base64 → 校验 length 与 bytes 一致 → 解封
```

任何一步失败都**不落盘、不覆盖本机**，只把状态置成 `'error'` 并在设置页显示原因。

## 5. 冲突与合并

本地维护三个值：`syncedRev`（最后一次成功同步到的 rev）、`dirty`（自那之后有没有改过）、
`deviceId`。

| 远端 rev | 本地 dirty | 动作 |
|---|---|---|
| == syncedRev | 否 | 无事可做 |
| == syncedRev | 是 | 推送（§4.3） |
| > syncedRev | 否 | 直接采纳远端：替换本地 vault，用内存里的 DEK 解密，刷新界面 |
| > syncedRev | 是 | **冲突**，见下 |
| < syncedRev | — | 远端比本机旧，说明别人拿旧数据覆盖过；按 dirty 决定推送或采纳 |

### 5.1 冲突处理：解密后按账户合并

因为两台设备共用同一个 DEK，冲突时**两边都能解密**，所以可以在明文层合并，
而不是粗暴地二选一。合并规则直接复用 `core/backup.ts` 里已有的 `planImport`：

- 只做加法，绝不覆盖
- 同 `issuer + account + secret` 视为同一条，跳过
- 同名不同密钥 → 两条都留，并在下次打开时提示（复用 `import.skip-summary` 那套文案）

合并结果用新 epoch 提交，rev + 1。这条路径走通之后，「两台设备各加了几个账户」
这种最常见的冲突会静默解决，用户看不到任何弹窗。

**失败兜底**：如果远端解不开（DEK 不同、密文损坏），不做任何合并，
状态置为 `'foreign-vault'`，设置页显示「云端的库和本机不是同一个，需要你决定保留哪一个」，
并给出「先导出本机备份」的按钮。绝不自动覆盖。

## 6. 设备 B 怎么加入（认领流程）

新设备装好扩展 → 库是空的。此时**不需要用户去设置里找开关**，空态就能接住：

```
打开扩展 → 未解锁/空库 → 读 sync:manifest
  ├─ 没有 manifest        → 正常空态（现状不变）
  └─ 有 manifest 且 vaultId 不同
       → 空态顶部出现一条：「云端有一个加密的库，输入密码恢复」
       → 点进去：输入密码 → 拉取 → 解封 → 替换本机 → 直接进入列表
```

三种情形：

| 本机库 | 处理 |
|---|---|
| 空库（新建、0 条） | 直接认领云端，无需确认。这是 90% 的场景（新电脑） |
| 非空、vaultId 不同 | **挡住**：先强制导出本机备份文件，再让用户选「用云端覆盖本机」或「把本机推上云」 |
| 非空、vaultId 相同 | 正常同步流程（§5） |

「强制先导出」不是保险起见，是必须：覆盖前不给退路的操作，在这个产品里一次都不该出现
（对齐 SPEC §0 的硬性红线：不能让用户永久失去自己的码）。

## 7. 安全模型

### 7.1 前置条件（硬约束）

**开启同步前必须已设密码。**

无密码时 `dekWrap` 是 `{ kind: 'none', dek: base64 }`——DEK 是明文。
把它同步上云 = 把明文密钥交给 Google。所以开关的可用性判断是：

```
可以开启 = 已设密码 && Chrome 商店安装 && sync 区可用
```

任一不满足，开关置灰并显示具体原因（不是一句「暂不可用」）。

### 7.2 威胁变化

| 威胁 | 现状 | 开启同步后 |
|---|---|---|
| 本机磁盘被读 | 密文，安全 | 不变 |
| Google 侧 | 无数据 | 看到密文 + vaultId + 时间戳 |
| Google 账号被盗 | 无影响 | 拿到 wrapped DEK，可**离线爆破密码** |
| 密码太弱 | 本机风险 | 风险放大到云端 |

第二、三行是必须承认的代价。缓解手段已经在代码里：PBKDF2 600k 迭代、
`checkPassword` 强度检查。**不需要新增机制，但要确认 `checkPassword` 的下限足够**
（P0 复测：8 位纯数字大概能扛多久，如果太短就为同步场景单独提一档要求）。

### 7.3 关闭同步

```
chrome.storage.sync.clear()
→ 提示：已从云端删除。其他设备上已经同步过去的副本不会自动消失，
        需要在那些设备上关闭同步或清除扩展数据。
```

这句必须写在界面上，不能只写在文档里。用户以为"关了就等于全删了"是最常见误解。

## 8. 触发时机与节流

| 时机 | 动作 |
|---|---|
| `mutate()` 成功后 | 标记 `dirty`，进入 2 秒 debounce 窗口 |
| debounce 到期 | 提交一次（§4.3） |
| 解锁成功 | 先拉一次远端，按 §5 判定 |
| `chrome.storage.onChanged`（sync 区，key 为 `sync:manifest`） | 按 §5 判定 |
| 弹窗打开 | 若距上次同步 > 5 分钟，后台拉一次 |

**`onChanged` 会因本机写入而触发**，必须用 `deviceId + rev` 过滤掉自己刚写的那笔，
否则会自己触发自己、反复刷新。

**节流理由**：`mutate` 每次都是全量重写 vault，连点几下设置就会写多次。
2 秒 debounce 把「改主题、改排序、拖账户」这类连续操作收成一次提交，
既有配额考虑，也避免列表频繁重渲染。

## 10. 必须处理的「静默失败」

这是这个方案最容易做砸的地方。

`chrome.storage.sync` **没有任何 API 能告诉你同步是否真的在工作**。
国内网络、用户关掉了 Chrome 同步的「扩展程序」分类、企业策略——这三种情况下
写入依然成功，数据只是留在本地排队，永远不会到达另一台设备。

**缓解**：在云端 manifest 之外，额外记 `local.lastPushedRev` 和 `local.lastSeenAt`。
如果「本地写入成功」但「接下来 24 小时没有从任何其他 deviceId 读到新的 rev」，
状态行降级成「已保存到本机，但还没有同步到其他设备」。
这是唯一能给用户的诚实信号。

## 12. 测试计划

| 层 | 用例 |
|---|---|
| 协议（纯函数） | 0 字节 / 1 条 / 300 条；6KB 边界；半套分片不可见；manifest 指向不存在的分片 |
| 提交 | 写分片中途失败 → 旧 manifest 仍可用；GC 只删 `epoch < current-1` |
| 冲突 | 双边各加 1 条 → 合并成 2 条；双边改同一条 → 不静默覆盖 |
| 容量 | 300 条能提交；350 条拒绝并给出准确上限 |
| 安全 | 无密码库不能开启；`dekWrap.kind === 'none'` 被拦 |
| 手工 | 两个 Chrome profile 同账号，各开一个弹窗，互看对方改动 |

最后一条是唯一无法自动化的，必须做——**这是唯一能验证 Chrome Sync 真的在传数据的办法**。

## 14. 风险

| 风险 | 概率 | 应对 |
|---|---|---|
| 用户开了开关但 Chrome 同步没在工作（国内） | 高 | §10 的诚实状态行；不承诺"一定同步" |
| 两台设备同时改导致数据错乱 | 中 | epoch 代际隔离 + 解密后合并，已覆盖 |
| 容量超限（300 条以上用户） | 低 | 提交前自检 + 明确错误文案 + 引导用导出备份 |
| 定位被用户质疑「说好不上传」 | 中 | 默认关闭 + 开关旁明确解释 + 不改商店宣传口径 |
| Google 侧政策/接口变化 | 低 | 所有读写收敛在 `platform/sync.ts` 一个文件，换通道只改这里 |

## 15. 一句话结论

技术上完全可行，成本 5.5 人日、零服务器；
**真正的代价不在代码，在于它把产品从「纯本地」挪到「默认本地、可选上云」**。
这个决定如果还没拍，先别开工。
